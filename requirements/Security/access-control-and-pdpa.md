## 1. เป้าหมายและบริบท (Goal & Context)

ระบบ **CU-PFIS (ระบบสารสนเทศคณะเภสัชศาสตร์ จุฬาลงกรณ์มหาวิทยาลัย / Chula Pharmacy Faculty Information System)** มีกลุ่มผู้ใช้งานหลักตามเอกสารขอบเขตหน้า 1 ได้แก่ **Admin (ดูแลระบบทั้งหมด)**, **เจ้าหน้าที่ (`Staff`)**, และ **อาจารย์ (`Faculty`)** (โดยอาจารย์เข้าใช้งานได้แบบเดียวกับ `CUPPEP`) และมีข้อกำหนดด้านการจำกัดสิทธิ์การมองเห็นข้อมูลในหลายเมนู เช่น:
- ข้อมูลบางประเภทจำกัดเฉพาะเจ้าหน้าที่เท่านั้น (เช่น การบริหารงบอบรมภาพรวม, การดาวน์โหลดไฟล์เล่มโครงการปริญญานิพนธ์, การดูผลประเมินผู้ใช้บัณฑิต, การดูรายละเอียดการนำไปใช้ประโยชน์ของโครงการ)
- อาจารย์เห็นและแก้ไขได้เฉพาะข้อมูลของตนเอง (เช่น CV อาจารย์ของตนเอง, คำขออบรมของตนเอง, และโครงการปริญญานิพนธ์ที่ตนเองเป็นอาจารย์ที่ปรึกษา)
- ข้อมูลส่วนบุคคลอ่อนไหว เช่น **เลขบัญชีธนาคารของอาจารย์** (สำหรับการเบิกเงินอบรม) ต้องจำกัดสิทธิ์เฉพาะผู้รับผิดชอบที่เกี่ยวข้องเท่านั้น

## 2. ขอบเขต (Scope)

### สิ่งที่ต้องทำในรอบนี้ (In scope)

- ระบบยืนยันตัวตน (Authentication) รองรับการเชื่อมต่อ SSO / บัญชีแบบเดียวกับ `CUPPEP` (และมี `FakeAuth` สำหรับสภาพแวดล้อมการพัฒนาในเครื่อง)
- ระบบกำหนดสิทธิ์แบบ `module.action` (`Permission` และ `RolePermission`) สำหรับบทบาทหลัก:
  1. `Admin` (ผู้ดูแลระบบทั้งหมด)
  2. `Staff` (เจ้าหน้าที่ฝ่ายวิชาการ / เจ้าหน้าที่ผู้รับผิดชอบ)
  3. `Faculty` (อาจารย์)
- การตรวจสอบสิทธิ์ระดับความเป็นเจ้าของข้อมูล (Resource Ownership Policy):
  - อาจารย์ดู/แก้ไข CV และคำขออบรมของตนเอง
  - อาจารย์ที่ปรึกษาโครงงานเห็นและกรอกข้อมูลการใช้ประโยชน์เฉพาะโครงงานที่ตนเองเป็นที่ปรึกษา (`req071169.pdf` หน้า 8)
- การปกป้องข้อมูลส่วนบุคคลตาม PDPA:
  - จำกัดการเข้าถึงและซ่อนเลขบัญชีธนาคารในคำขออบรมจากผู้ไม่มีสิทธิ์และจากรายงานทั่วไป
  - จำกัดการเข้าถึงผลประเมินผู้ใช้บัณฑิตและไฟล์เล่มโครงงานตามสิทธิ์ที่กำหนด
  - บันทึก `AuditLog` ทุกการสร้าง/แก้ไข/ลบ/เปลี่ยนสถานะ โดยไม่บันทึกข้อมูลอ่อนไหวลง Plaintext Application Log

### สิ่งที่ไม่รวมในรอบนี้ (Out of scope)

- การจัดการสิทธิ์ภายในระบบ `CUPPEP` เดิม (ระบบ `CU-PFIS` จัดการสิทธิ์เฉพาะภายในเว็บแอปพลิเคชันใหม่และ API ที่เชื่อมต่อกัน)

## 3. ศัพท์ที่เกี่ยวข้อง (Domain terms)

- **Role (บทบาทผู้ใช้งาน):** `Admin`, `Staff` (เจ้าหน้าที่), `Faculty` (อาจารย์)
- **Permission (`module.action`):** สิทธิ์ย่อยระดับการกระทำ เช่น `faculty-cv.view-all`, `faculty-cv.edit-own`, `training-requests.verify`, `training-requests.approve`, `training-requests.view-bank-account`, `senior-projects.download-file`
- **Resource Ownership (ความเป็นเจ้าของข้อมูล):** เงื่อนไขที่ผูกบัญชีผู้ใช้งานเข้ากับ `FacultyMemberId` เพื่อตรวจสิทธิ์ว่าเป็นข้อมูลของตนเองหรือเป็นที่ปรึกษาโครงงานนั้นหรือไม่

## 4. ข้อมูล/ฟิลด์ที่เกี่ยวข้อง (Data / Fields)

| ชื่อฟิลด์ (ไทย) | ชื่อฟิลด์ (English) | ประเภทข้อมูล | บังคับ/ไม่บังคับ | แหล่งข้อมูล (CU-PFIS / CUPPEP / Sheet) | กติกา/validation |

## 5. ความสัมพันธ์กับข้อมูลอื่นและการเชื่อมต่อภายนอก (Relationships & External Sync)

- เชื่อมโยงผู้ใช้งานที่มีบทบาท `Faculty` เข้ากับ `FacultyMember` ใน `Faculty` Context
- ทำงานร่วมกับ `AuthorizationBehaviour` ใน MediatR Pipeline เพื่อตรวจ `[RequirePermission]` ก่อนเข้าถึง Handler ทุกตัว
- ทำงานร่วมกับ `AuditableEntitySaveChangesInterceptors` เพื่อบันทึกผู้ทำรายการ (`CreatedBy`, `LastModifiedBy`) ลงฐานข้อมูลและ `AuditLog`

## 6. กติกาทางธุรกิจและลำดับสถานะ (Business Rules & Workflow States)

1. **ห้ามตรวจสิทธิ์เฉพาะการซ่อนเมนูหน้าบ้าน (UI):** ทุก Command และ Query ใน Backend ต้องตรวจสิทธิ์ผ่าน `[RequirePermission]` และตรวจ Resource Ownership เสมอ
2. **สิทธิ์ตามตารางสรุปหน้า 10–12 ของ `req071169.pdf`:**
   - **CV อาจารย์:** เจ้าหน้าที่เห็นทั้งหมด / อาจารย์เห็นรายบุคคล (ของตนเอง)
   - **การอบรม:** เจ้าหน้าที่เห็นทั้งหมดและกดตรวจสอบ/อนุมัติ / อาจารย์กรอกข้อมูลและดูประวัติของตนเอง
   - **นิสิต (CV นิสิต, ผลงาน, การได้งานทำ, ผู้ใช้บัณฑิต) และใบประกอบวิชาชีพ:** แสดงผลให้เจ้าหน้าที่ดูแลและตรวจสอบ
   - **เล่มโครงการปริญญานิพนธ์ (PDF):** เจ้าหน้าที่อัปโหลดและเข้าถึงไฟล์ได้เท่านั้น (`รอยืนยัน Q10 เรื่องความหมายของปุ่ม Publish`)
   - **การนำไปใช้ประโยชน์ของโครงการ:** อาจารย์เห็นและกรอกเฉพาะโครงการที่ตนเองเป็นที่ปรึกษา / เจ้าหน้าที่เห็นทั้งหมด
3. **การคุ้มครองข้อมูลบัญชีธนาคาร (`BankAccountInfo`):** เฉพาะเจ้าของคำขอและเจ้าหน้าที่ที่มีสิทธิ์ด้านการเงิน/อนุมัติ (`training-requests.view-bank-account`) เท่านั้นที่เรียกดูได้

## 8. สิทธิ์การเข้าถึงและข้อมูลส่วนบุคคล (Permissions & PDPA)

- `security.users.manage`, `security.roles.manage` — เฉพาะ `Admin`
- บังคับใช้ PDPA masking/projection ในระดับ Query DTO เพื่อไม่ให้ฟิลด์อ่อนไหวหลุดออกไปใน API ทั่วไป และห้ามเขียนชื่อ-นามสกุลหรือเลขบัญชีลงใน Application Log

## 9. หน้าจอและการส่งออกรายงาน (UI / Frontend & Exports)

- หน้าจัดการผู้ใช้งานและกำหนดบทบาท/สิทธิ์ (`list`, `create`, `edit/[id]`, `view/[id]`) สำหรับ `Admin`
- การส่งชุดสิทธิ์ (`permissions`) ให้ Frontend (`CASL`) เพื่อควบคุมการแสดงผลเมนูและปุ่มตามสิทธิ์จริง

## 10. เกณฑ์การยอมรับ (Acceptance Criteria)

- [ ] เมื่อผู้ใช้ที่ไม่ได้รับสิทธิ์เรียกใช้งาน API Endpoint โดยตรง ระบบต้องตอบกลับ `403 Forbidden`
- [ ] เมื่ออาจารย์เข้าดูเมนูโครงการปริญญานิพนธ์เพื่อกรอกการใช้ประโยชน์ ระบบจะแสดงเฉพาะโครงการที่อาจารย์ท่านนั้นเป็นที่ปรึกษาเท่านั้น
- [ ] เมื่อผู้ใช้ทั่วไปหรือผู้ไม่มีสิทธิ์ด้านการเงินดึงข้อมูลการอบรม ข้อมูลเลขบัญชีธนาคารจะต้องไม่ถูกส่งกลับมาใน Response

## 11. เคสที่ต้องทดสอบ (Test Cases)

### กรณีสำเร็จ (Happy path)
- `Admin` กำหนดสิทธิ์ให้ `Staff` และ `Faculty` → ผู้ใช้แต่ละบทบาทเข้าถึงข้อมูลได้ตามขอบเขตที่กำหนด

### กรณีข้อมูลไม่ถูกต้อง / สิทธิ์ไม่พอ
- `Faculty` พยายามแก้ไข CV ของอาจารย์ท่านอื่น หรือพยายามดูโครงงานที่ตนเองไม่ได้เป็นที่ปรึกษา → ระบบปฏิเสธ (`403 Forbidden`)
- `Faculty` พยายามกดอนุมัติคำขออบรมด้วยตนเอง → ระบบปฏิเสธ (`403 Forbidden`)
